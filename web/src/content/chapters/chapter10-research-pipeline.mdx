# Research Pipeline Utilities for Causal Inference

## Introduction

Chapters 1–9 developed the theory, methodology, and validation of Double Machine Learning for causal inference. This chapter sketches research pipeline utilities for organizing model versions, diagnostics, and retraining decisions. The companion repo code is not a production deployment framework; it is a book companion that illustrates the additional requirements a real deployment would need to satisfy.

<ResultBox>

**Chapter objectives:**

- Understand why deployed causal inference differs from standard ML.
- Design model serialization for DML's two-stage architecture.
- Sketch inference API contracts for treatment effect estimation.
- Implement causal-specific monitoring (not just prediction accuracy).
- Create intelligent retraining triggers based on causal validity.
- Assemble reproducible research/demo pipelines.

</ResultBox>

### The production paradox

Standard machine learning production systems monitor prediction accuracy against ground truth. A deployed image classifier can be evaluated against labeled images. A recommendation system can be evaluated by click-through rates. The feedback loop is direct: prediction $\rightarrow$ observation $\rightarrow$ accuracy.

Causal inference breaks this paradigm fundamentally:

<InsightBox>

**The fundamental problem of production causal inference.** We **cannot directly monitor treatment effect accuracy** in production because counterfactual outcomes are never observed. A system predicting "treatment would increase retention by 5%" cannot be validated by observing both outcomes for the same unit.

</InsightBox>

This creates a production monitoring challenge without parallel in standard ML. Instead of monitoring prediction accuracy, we must monitor the *conditions under which our estimates remain valid*:

1. **Overlap violations** (positivity breakdown).
2. **Treatment distribution shift** (assignment mechanism change).
3. **Nuisance model degradation** (first-stage fit quality).
4. **Effect stability** (is the treatment effect itself changing?).

**Production monitoring: standard ML vs. causal inference**

| Aspect | Standard ML | Causal inference |
|---|---|---|
| Ground truth | Observable | Never observable |
| Primary metric | Prediction accuracy | Nuisance fit quality |
| Feature drift | Monitor input distribution | Monitor treatment distribution |
| Overlap | N/A | Critical (positivity) |
| Retraining trigger | Accuracy degradation | Identification breakdown |
| Validation | Holdout set | Refutation tests |

## Model serialization for DML

DML models have a unique architecture requiring specialized serialization.

### Components to serialize

A deployment-oriented DML model would need to serialize:

1. **Nuisance models** for each cross-fitting fold:
   - For a continuous treatment, store models for $\mathbb{E}[T\mid X]$ and $\mathbb{E}[Y\mid X]$.
   - For a binary treatment, store a propensity model and outcome regressions for both treatment arms.
2. **Cross-fitting configuration** (K folds, temporal blocking).
3. **Feature preprocessing** fitted on each learner's training sample.
4. **HAC parameters** for time series standard errors.
5. **Training metadata** (data snapshot, hyperparameters).

```python
@dataclass
class DMLModelVersion:
    """Versioned DML model with full serialization support."""

    version_id: str  # Unique hash-based identifier
    created_at: str
    model_type: str  # "double_ml", "temporal_plr_dml", etc.
    n_folds: int

    # Serialized nuisance models by fold
    nuisance_models: Dict[int, Tuple[bytes, bytes]]

    # Feature specification
    feature_names: List[str]
    treatment_name: str
    outcome_name: str

    # Reproducibility
    hyperparameters: Dict[str, Any]
    metrics: Dict[str, float]  # R² propensity, R² outcome

    @classmethod
    def create(
        cls,
        model_type: str,
        nuisance_models: Dict[int, Tuple[Any, Any]],
        feature_names: List[str],
        treatment_name: str,
        outcome_name: str,
        hyperparameters: Dict[str, Any],
        **kwargs,
    ) -> "DMLModelVersion":
        """Create versioned model with content-based hash."""
        # Serialize nuisance models per fold
        serialized = {}
        for fold_idx, (prop, out) in nuisance_models.items():
            serialized[fold_idx] = (
                pickle.dumps(prop),
                pickle.dumps(out),
            )

        # Generate version ID from content hash
        timestamp = datetime.utcnow().isoformat()
        version_id = f"dml-{compute_hash(...)[:12]}"

        return cls(version_id=version_id, ...)
```

### Model registry operations

A DML-aware model registry supports:

- **Registration**: store versioned models with full metadata.
- **Retrieval**: load a specific version for inference.
- **Promotion**: candidate $\rightarrow$ active workflow.
- **Rollback**: revert to a previous active version.
- **Lineage**: track which data/config produced which model.

```python
# Initialize registry
registry = DMLModelRegistry("./models/dml_registry")

# After training
version_id = registry.register(model_version)

# Demo promotion workflow
registry.promote_to_staging(version_id)

# After validation passes
registry.promote_to_production()

# If issues detected
registry.rollback(to_version="dml-abc123")
```

### Persistence format

Models are persisted as directories containing:

```
dml-abc123xyz/
├── metadata.json          # Version info, hyperparameters
├── propensity_fold_0.pkl  # Serialized propensity model
├── outcome_fold_0.pkl     # Serialized outcome model
├── propensity_fold_1.pkl
├── outcome_fold_1.pkl
├── ...
└── feature_transformer.pkl  # Optional scaler/encoder
```

This structure enables atomic updates (complete version or nothing), efficient fold-level updates (not the full model), human-readable metadata inspection, and Git-compatible versioning (track `metadata.json`).

## Inference APIs

Deployed inference for causal models differs from standard ML prediction.

### Batch vs. real-time inference

**Inference patterns for causal models**

| Pattern | Use case | Latency |
|---|---|---|
| Batch scoring | Periodic CATE updates for all customers | Minutes |
| Real-time API | On-demand treatment decisions | Under 100ms |
| Streaming | Continuous effect monitoring | Sub-second |

### API design for CATE estimation

A hypothetical deployed CATE API would need to provide:

```python
class CATEInferenceAPI:
    """Hypothetical API for treatment effect estimation."""

    def estimate_cate(
        self,
        features: Dict[str, Any],
        return_confidence: bool = True,
    ) -> CATEResponse:
        """
        Estimate conditional treatment effect.

        Args:
            features: Covariate values for the unit
            return_confidence: Include confidence intervals

        Returns:
            CATEResponse with effect estimate and metadata
        """
        X = self._transform_features(features)

        # Compute CATE using averaged nuisance models
        cate = self._compute_cate(X)

        # Compute confidence interval
        ci_lower, ci_upper = self._compute_ci(X, cate)

        # Check overlap (propensity extremity)
        propensity = self._predict_propensity(X)
        overlap_warning = self._check_overlap(propensity)

        return CATEResponse(
            cate=cate,
            ci_lower=ci_lower,
            ci_upper=ci_upper,
            propensity=propensity,
            overlap_warning=overlap_warning,
            model_version=self._current_version,
        )
```

### Response structure

A complete CATE response includes uncertainty and validity flags:

```python
@dataclass
class CATEResponse:
    cate: float           # Point estimate
    ci_lower: float       # 95% CI lower
    ci_upper: float       # 95% CI upper
    propensity: float     # P(T=1|X) for this unit
    overlap_warning: bool # True if propensity extreme
    model_version: str    # For reproducibility
    timestamp: str        # Inference timestamp
```

<InsightBox>

**Always return propensity with CATE.** Including the propensity score in CATE responses enables downstream systems to filter or down-weight estimates with poor overlap. A CATE estimate with $\hat{e}(X) = 0.001$ is extrapolation, not estimation.

</InsightBox>

## Causal-specific monitoring

The heart of production causal inference is monitoring the *conditions for valid inference*, not prediction accuracy.

### Overlap violations (positivity)

The positivity assumption requires $0 < P(T=1 \mid X) < 1$ for all $X$. In practice, we need propensity scores bounded away from 0 and 1:

$$
\epsilon < \hat{e}(X) < 1 - \epsilon, \quad \text{typically } \epsilon = 0.01
$$

```python
def check_overlap_violations(
    propensity_scores: np.ndarray,
    clip_min: float = 0.01,
    clip_max: float = 0.99,
) -> MonitoringResult:
    """Check for positivity violations."""

    too_low = propensity_scores < clip_min
    too_high = propensity_scores > clip_max
    violation_rate = (np.sum(too_low) + np.sum(too_high)) / len(propensity_scores)

    if violation_rate >= 0.10:  # >10% violations
        level = AlertLevel.CRITICAL
        message = f"CRITICAL: {violation_rate:.1%} overlap violations"
    elif violation_rate >= 0.05:
        level = AlertLevel.WARNING
        message = f"WARNING: {violation_rate:.1%} overlap violations"
    else:
        level = AlertLevel.OK
        message = f"Overlap OK: {violation_rate:.1%} violations"

    return MonitoringResult(
        check_name="overlap_violations",
        level=level,
        value=violation_rate,
        message=message,
    )
```

### Treatment distribution shift

Unlike standard feature drift, treatment distribution shift indicates the *assignment mechanism* may have changed. This is causal-specific:

- Standard ML: features changed $\rightarrow$ model may underfit.
- Causal inference: treatment assignment changed $\rightarrow$ **identification may fail**.

```python
def check_treatment_shift(
    treatment_current: np.ndarray,
    treatment_baseline: np.ndarray,
) -> MonitoringResult:
    """Detect treatment distribution shift."""

    # For binary treatment: proportion difference
    # For continuous: KS statistic
    if is_binary(treatment_current):
        p_current = np.mean(treatment_current)
        p_baseline = np.mean(treatment_baseline)
        metric = abs(p_current - p_baseline)
    else:
        metric, _ = ks_2samp(treatment_current, treatment_baseline)

    if metric >= 0.10:
        level = AlertLevel.CRITICAL
        message = "Treatment assignment mechanism may have changed"
    # ...
```

### Nuisance model degradation

DML validity requires well-fitting nuisance models. We monitor nuisance $R^2$, not treatment effect accuracy (which is unknowable). The two models are judged separately. An outcome $R^2$ below 0.30 is critical and one below 0.50 a warning, the thresholds of earlier versions; a low outcome $R^2$ can mean a poor outcome model or an outcome that is mostly noise, and the monitor cannot tell the two apart. A treatment $R^2$ below 0.50 is only a warning, never critical: a randomized treatment has an $R^2$ near zero by design, and the monitor cannot tell that case from a treatment model that misses confounders.

```python
def check_nuisance_degradation(
    r2_propensity: float,
    r2_outcome: float,
    warning_threshold: float = 0.50,
    critical_threshold: float = 0.30,
) -> MonitoringResult:
    """Check nuisance model fit quality, one rule per model."""

    # Outcome model: a poor fit can bias the effect estimate.
    if r2_outcome < critical_threshold:
        level = AlertLevel.CRITICAL
    elif r2_outcome < warning_threshold:
        level = AlertLevel.WARNING
    else:
        level = AlertLevel.OK

    # Treatment model: a low R^2 is a warning, never critical.
    if r2_propensity < warning_threshold and level == AlertLevel.OK:
        level = AlertLevel.WARNING

    return MonitoringResult(...)
```

<InsightBox>

**Why we monitor nuisance $R^2$ instead of effect accuracy.** The DML bias term depends on the product of nuisance errors:

$$
\text{Bias} \propto \|\hat{m} - m_0\| \cdot \|\hat{e} - e_0\|
$$

Poor nuisance fit indicates potential bias. But we cannot directly measure treatment effect accuracy because counterfactuals are unobserved.

</InsightBox>

### Effect stability

Large changes in estimated treatment effects over time warrant investigation. When both estimates carry a standard error, the change is measured in standard errors, $z = (\hat\theta_{\text{current}} - \hat\theta_{\text{baseline}}) / \sqrt{\text{se}_{\text{current}}^2 + \text{se}_{\text{baseline}}^2}$. When a standard error is missing, the monitor falls back to the relative change:

```python
def check_effect_stability(
    current_effect: float,
    baseline_effect: float,
    current_se: Optional[float] = None,
    baseline_se: Optional[float] = None,
    z_warning: float = 1.96,
    z_critical: float = 3.0,
) -> MonitoringResult:
    """Monitor treatment effect stability over time."""

    if current_se is not None and baseline_se is not None:
        # Both standard errors given: the change in standard errors.
        combined_se = np.sqrt(current_se**2 + baseline_se**2)
        z = (current_effect - baseline_effect) / combined_se
        metric, warning, critical = abs(z), z_warning, z_critical
    else:
        # A standard error missing: the relative change.
        if abs(baseline_effect) < 1e-10:
            metric = float("inf") if abs(current_effect) > 1e-10 else 0.0
        else:
            metric = abs(current_effect - baseline_effect) / abs(baseline_effect)
        warning, critical = 0.20, 0.50

    if metric >= critical:
        level = AlertLevel.CRITICAL
    elif metric >= warning:
        level = AlertLevel.WARNING
    else:
        level = AlertLevel.OK
    # ...
```

The two rules can disagree. A 60% change of a noisy estimate (0.05 to 0.08, both standard errors 0.20) is $z = 0.11$, which is no alert, although the relative rule would call it critical. A 15% change of a precise estimate (10.0 to 8.5, both standard errors 0.01) is $z = -106$, which is critical, although the relative rule would call it stable.

Effect changes may indicate genuine time-varying effects (valid, requires dynamic modeling), model degradation (problematic), selection/survivorship bias in new data (problematic), or a changed treatment definition (problematic).

## Retraining triggers

Standard ML retraining triggers focus on prediction accuracy degradation. Causal inference requires different triggers aligned with identification assumptions.

### Causal-specific triggers

**Retraining triggers: standard ML vs. causal inference**

| Standard ML | Causal inference | Rationale |
|---|---|---|
| Accuracy drop | — | Counterfactuals unobserved |
| Feature drift | Covariate drift | Affects nuisance models |
| Class imbalance | Treatment shift | Assignment mechanism changed |
| — | Overlap violations | Positivity breakdown |
| — | Nuisance $R^2$ drop | DML validity threatened |
| Scheduled | Scheduled | Preventive maintenance |

### Scheduler design

```python
class RetrainScheduler:
    """Intelligent retraining scheduler for DML pipelines."""

    def __init__(self, config: RetrainSchedulerConfig):
        self.config = config
        self.monitor = CausalMonitor()

    def evaluate_retrain_need(
        self,
        monitoring_results: List[MonitoringResult],
        n_samples: int,
    ) -> Optional[RetrainTrigger]:
        """Evaluate if retraining is needed."""

        # Check cooldown (avoid excessive retraining)
        if self.is_in_cooldown():
            return None

        # Check minimum sample threshold
        if n_samples < self.config.min_samples:
            return None

        # Map monitoring results to triggers
        for result in monitoring_results:
            if result.level == AlertLevel.CRITICAL:
                return RetrainTrigger(
                    trigger_type=self._result_to_trigger_type(result),
                    severity=AlertLevel.CRITICAL,
                    reason=result.message,
                )

        # Check scheduled retraining
        return self.check_scheduled_retrain()
```

### Trigger types

```python
class TriggerType(Enum):
    SCHEDULED = "scheduled"           # Time-based
    OVERLAP_VIOLATION = "overlap"     # Positivity breakdown
```

### InsuranceDMLPipeline implementation

Each fold fits its own feature scalers and nuisance models on the training rows. With a time column configured, supply one series in chronological order. The estimator scores dates having held-out predictions. The initial training block supplies history for the first fold. The result records both the total and the scored sample counts.

For continuous treatment, let $v_i=T_i-\hat m(X_i)$ and $u_i=Y_i-\hat\ell(X_i)$ be held-out residuals. The fitted slope and influence score use the same scored rows:

$$
\hat\theta=\frac{\sum_i v_i u_i}{\sum_i v_i^2},
\qquad
\hat\psi_i=\frac{v_i(u_i-\hat\theta v_i)}{n_{\mathrm{used}}^{-1}\sum_j v_j^2}.
$$

For binary treatment, each fold fits an assignment probability $\hat e$ and two outcome means $\hat\mu_a(X)=\widehat{\mathbb{E}}[Y\mid T=a,X]$. The implementation clips predicted probabilities to $[0.01,0.99]$ before dividing. The average treatment effect is the mean of the held-out augmented inverse-probability-weighted outcomes

$$
h_i = \hat\mu_1-\hat\mu_0 + \frac{T_i(Y_i-\hat\mu_1)}{\hat e}
       -\frac{(1-T_i)(Y_i-\hat\mu_0)}{1-\hat e}.
$$

The binary influence score is $h_i-\bar h$. For either treatment, the independent-observation SE is the score's sample standard deviation divided by $\sqrt{n_{\mathrm{used}}}$. With HAC enabled, the pipeline uses the long-run variance of these scores in date order. Probability-overlap monitoring uses the original, unclipped predictions in the binary example. For continuous treatment, identification requires residual variation in the dose. Each serialized fold keeps its fitted preprocessing with its models.

## Insurance pricing case study

### Two simulated retention studies

Consider two simulated insurance retention studies, each observing one customer decision per period at 400 ordered dates. In the price study, the treatment is a competitor's price difference measured in tens of dollars. By construction each additional ten dollars raises the probability of retention by 0.10, holding the controls fixed. In the offer study, a binary renewal offer raises retention probability by 0.20. The two outcomes are simulated separately on the same covariate history.

Four expanding folds use 80 dates for the initial training block and score the following 320 dates. Both fits use linear outcome regressions, with one regression per arm for the offer. The continuous price model is linear and the binary assignment model uses logistic regression. Each interval uses Bartlett HAC with four lags and a normal critical value of 1.96.

```python
from tempfile import TemporaryDirectory

import numpy as np
from sklearn.linear_model import LinearRegression, LogisticRegression
from dml_ts.production import InsuranceDMLPipeline, PipelineConfig

rng = np.random.default_rng(42)
x = rng.uniform(-1, 1, (400, 2))
price = x[:, 0] + rng.uniform(-1, 1, len(x))
retained = rng.binomial(1, 0.50 + 0.10 * price + 0.10 * x[:, 1])
offer = rng.binomial(1, 0.50 + 0.20 * x[:, 0])
renewed = rng.binomial(1, 0.35 + 0.20 * offer + 0.10 * x[:, 1])

with TemporaryDirectory() as registry:
    def fit(treatment, outcome, treatment_model):
        config = PipelineConfig(
            n_folds=4, time_column="period", hac_bandwidth=4,
            model_registry_path=registry,
            propensity_model=treatment_model,
            outcome_model=LinearRegression(),
        )
        return InsuranceDMLPipeline(config).fit(x, treatment, outcome)

    slope = fit(price, retained, LinearRegression())
    per_dollar = fit(10 * price, retained, LinearRegression())
    ate = fit(offer, renewed, LogisticRegression())
    shifted = fit(offer, renewed + 100, LogisticRegression())
```

### Measured effects and uncertainty

**Synthetic retention estimates at 320 scored dates.** Effects are changes in retention probability per unit of the stated contrast.

| Contrast | Truth | Estimate | SE | 95% interval |
|---|---:|---:|---:|---:|
| Ten-dollar price change | 0.1000 | 0.1184 | 0.0510 | [0.0184, 0.2184] |
| One-dollar price change | 0.0100 | 0.0118 | 0.0051 | [0.0018, 0.0218] |
| Renewal offer | 0.2000 | 0.2325 | 0.0543 | [0.1261, 0.3390] |
| Offer, outcome plus 100 | 0.2000 | 0.2325 | 0.0543 | [0.1261, 0.3390] |

A price change of one dollar is one tenth of the first row's exposure contrast. Reporting price in dollars divides the slope, its SE and both interval endpoints by ten. The binary rows add 100 to every outcome as a check on the measurement scale. Both treatment-arm outcome models shift by the same amount, so the offer effect and its uncertainty stay the same. Each row summarizes a single simulated dataset. Repeated independent datasets would be needed to estimate coverage.
